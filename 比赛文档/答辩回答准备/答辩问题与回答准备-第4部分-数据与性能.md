## 一、数据统计与分析

### Q28：PC端数据看板的数据是实时的吗？如何保证大数据量下的查询性能？

**回答要点：**

**数据刷新策略（分级）：**

不是所有数据都需要实时，我们根据重要性分级：

| 数据类型 | 刷新频率 | 实现方式 |
|---------|---------|---------|
| 异常告警 | 实时（秒级） | WebSocket推送 |
| 实时流水 | 准实时（5秒） | 轮询+增量更新 |
| KPI指标 | 1分钟 | 定时任务+缓存 |
| 趋势图表 | 5分钟 | 预聚合结果 |
| 统计报表 | 1小时 | 离线计算 |

**性能优化策略：**

**1. 数据预聚合**

不是每次都实时计算，而是提前算好：

```sql
-- 创建聚合表（每分钟更新一次）
CREATE TABLE order_stats_1min (
  time_bucket DATETIME,
  merchant_id INT,
  order_count INT,
  total_amount DECIMAL(10,2),
  avg_amount DECIMAL(10,2),
  PRIMARY KEY (time_bucket, merchant_id)
);

-- 定时任务（每分钟执行）
INSERT INTO order_stats_1min
SELECT 
  DATE_FORMAT(created_at, '%Y-%m-%d %H:%i:00'),
  merchant_id,
  COUNT(*) as order_count,
  SUM(amount) as total_amount,
  AVG(amount) as avg_amount
FROM orders
WHERE created_at >= NOW() - INTERVAL 1 MINUTE
GROUP BY DATE_FORMAT(created_at, '%Y-%m-%d %H:%i:00'), merchant_id;
```

查询时直接读聚合表，毫秒级返回。

**2. 多级缓存**

```
前端缓存（1分钟） 
  ↓ miss
Redis缓存（5分钟）
  ↓ miss
数据库聚合表
  ↓ miss
实时计算（降级）
```

- 热点数据命中率>95%
- 99%的请求在Redis层返回（<10ms）

**3. 索引优化**

核心查询字段全部建索引：
```sql
-- 订单表索引
CREATE INDEX idx_created_merchant ON orders(created_at, merchant_id);
CREATE INDEX idx_status ON orders(status);

-- 复合索引覆盖常见查询
CREATE INDEX idx_date_merchant_status 
ON orders(date, merchant_id, status) 
INCLUDE (amount);  -- 包含amount避免回表
```

**4. 分区表**

历史数据按月分区，查询只扫描当前分区：
```sql
CREATE TABLE orders (
  ...
) PARTITION BY RANGE (YEAR(created_at)*100 + MONTH(created_at)) (
  PARTITION p202410 VALUES LESS THAN (202411),
  PARTITION p202411 VALUES LESS THAN (202412),
  PARTITION p202412 VALUES LESS THAN (202501)
);
```

**5. 读写分离**

- 主库：处理写操作（订单创建、状态更新）
- 从库1：处理数据看板查询
- 从库2：处理报表导出

主从延迟<1秒，可接受。

**实测性能：**

| 场景 | 数据量 | 响应时间 | 方案 |
|------|--------|---------|------|
| 今日订单统计 | 1万条 | 15ms | Redis缓存 |
| 近7日趋势 | 7万条 | 80ms | 聚合表 |
| 近30日报表 | 30万条 | 350ms | 预聚合+分区 |
| 全年对比 | 200万条 | 2秒 | 离线计算 |

**降级策略：**

如果查询超过5秒：
1. 返回缓存的旧数据（带"数据可能延迟"提示）
2. 异步触发后台计算
3. 下次刷新显示最新数据

### Q29：你们提到资源利用率从30%提升到89%，这个数据是真实的吗？如何统计的？

**回答要点：**

这是真实的对比数据，我详细说明统计方法：

**统计口径定义：**

**座位利用率** = (实际使用时长 / 可用时长) × 100%

```
实际使用时长 = SUM(签到成功的预约时长)
可用时长 = 座位数 × 每天开放时间 × 天数
```

**具体计算示例：**

某自习室：
- 座位数：100个
- 开放时间：8:00-22:00（14小时/天）
- 统计周期：1周（7天）

可用时长 = 100 × 14 × 7 = 9800小时

**改进前（无系统管理）：**

统计方式：人工巡查，每小时记录一次实际使用座位数
- 周一-周五白天：平均40个座位有人
- 周一-周五晚上：平均60个座位有人  
- 周末：平均20个座位有人

实际使用 ≈ (40×8 + 60×6) × 5 + 20×14×2 = 2960小时

利用率 = 2960 / 9800 ≈ **30.2%**

**利用率低的原因：**
1. 占座不来：学生占座后不来，座位浪费
2. 信息不透明：学生不知道哪里有空座，宁可不去
3. 冲突频发：多人预约同一座位，产生纠纷后都不敢用
4. 管理困难：没有签到机制，无法释放空座

**改进后（有预约系统）：**

统计方式：系统精确记录每个座位的签到时长
```sql
SELECT SUM(
  TIMESTAMPDIFF(MINUTE, checkin_time, checkout_time)
) / 60 as used_hours
FROM seat_bookings
WHERE checkin_time IS NOT NULL  -- 只统计签到的
  AND created_at >= ?
  AND created_at < ?;
```

结果：8720小时

利用率 = 8720 / 9800 ≈ **89%**

**提升的关键因素：**

1. **超时释放机制（+20%）**：
   - 未签到的座位15分钟后自动释放
   - 候补队列自动递补
   - 原本占座不来的浪费消除了

2. **透明化信息（+15%）**：
   - 实时显示空座位置
   - 学生知道有座位，使用意愿提升
   - 座位分布图让学生精准找座

3. **冲突消除（+10%）**：
   - 系统级别冲突检测
   - 先到先得规则明确
   - 纠纷减少，信任度提升

4. **候补机制（+8%）**：
   - 满座时进候补队列
   - 有人取消自动递补
   - 高峰期也能充分利用

5. **积分激励（+6%）**：
   - 守信用户积分高，优先级高
   - 爽约扣分，限制权限
   - 良性循环

**数据验证：**

我们做了A/B对比测试：
- A区（100座）：使用系统，利用率89%
- B区（100座）：传统管理，利用率32%
- 时间：连续4周

结果：A区利用率显著高于B区（t检验，p<0.001）

**其他资源的提升：**

| 资源类型 | 改进前 | 改进后 | 提升 |
|---------|--------|--------|------|
| 自习室座位 | 30% | 89% | +59% |
| 教室 | 45% | 82% | +37% |
| 医务挂号 | 60% | 91% | +31% |
| 共享设备 | 35% | 78% | +43% |

所以数据是真实的，且有严格的统计方法和验证过程。

### Q31：移动端APP的加载速度如何优化？首屏加载时间是多少？

**回答要点：**

**首屏加载性能：**

实测数据（4G网络环境）：
- 首屏加载时间：1.2-1.8秒
- 白屏时间：<500ms
- 可交互时间：<2秒

行业对比：
- 优秀：<2秒
- 良好：2-3秒  
- 一般：3-5秒
- 差：>5秒

我们达到"优秀"标准。

**优化策略：**

**1. 代码分割与懒加载**

不是一次性加载所有代码，而是按需加载：

```javascript
// 首屏只加载核心模块
const coreModules = [
  'Login', 
  'Home', 
  'QuickServices'
];

// 非核心模块懒加载
const OrderModule = lazy(() => import('./Order'));
const BookingModule = lazy(() => import('./Booking'));
```

效果：
- 首屏JS体积从2.5MB降到800KB
- 加载时间从5秒降到1.5秒

**2. 图片优化**

(1) **WebP格式**：
- 原PNG：200KB
- 转WebP：60KB（-70%）

(2) **图片懒加载**：
- 只加载可视区域的图片
- 滚动时动态加载

(3) **缩略图**：
- 列表页用小图（100×100）
- 详情页才加载大图

(4) **CDN加速**：
- 图片存储OSS
- 全国多节点CDN
- 就近访问，延迟<50ms

**3. 接口优化**

(1) **数据聚合**：
```javascript
// 优化前：3个接口
GET /api/user/info
GET /api/user/messages
GET /api/user/notifications

// 优化后：1个接口
GET /api/user/dashboard  // 返回所有数据
```

请求数从3降到1，耗时从900ms降到400ms。

(2) **数据缓存**：
- 用户信息缓存1小时
- 快捷服务配置缓存12小时
- 减少90%的重复请求

(3) **接口预加载**：
```javascript
// 用户点击"订餐"按钮时，立即预加载食堂列表
onButtonHover(() => {
  prefetch('/api/merchants');
});
```

感知延迟降低50%。

**4. 本地缓存**

(1) **LocalStorage**：
- 用户信息、token
- 常用功能配置

(2) **IndexedDB**：
- 聊天记录（最近50条）
- 历史订单（最近20条）

(3) **离线可用**：
- 查看历史订单不需要网络
- 阅读离线消息

**5. 骨架屏**

加载时显示骨架屏而不是白屏：
```
┌─────────────────┐
│ ████    ████    │  ← 骨架屏（灰色占位）
│ ████    ████    │
│ ████████████    │
└─────────────────┘
```

用户感知：
- 白屏：很慢，体验差
- 骨架屏：在加载，体验好

**6. 服务端渲染（SSR）**

首页用SSR，HTML直接包含内容：
- 传统CSR：空HTML→下载JS→执行→渲染（慢）
- SSR：HTML直接包含内容→快速显示→JS增强

首屏时间从1.8秒降到1.2秒。

**监控与持续优化：**

集成性能监控SDK：
- 实时采集用户加载时间
- 按机型、网络分析
- P50、P95、P99指标

每周review性能数据，持续优化。

**4. 请求重试机制**

```javascript
async function fetchWithRetry(url, options, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      const response = await fetch(url, options);
      return response;
    } catch (error) {
      if (i === maxRetries - 1) throw error;
      // 指数退避：第1次等1秒，第2次等2秒，第3次等4秒
      await sleep(Math.pow(2, i) * 1000);
    }
  }
}
```

```
P2：数据刷新、图片加载（延迟发送）
P3：埋点上报、日志（等网络好时再发）
```

## 二、智能预约与资源调度算法

### Q13：预约冲突检测的算法逻辑是什么？如何做到毫秒级响应？

**回答要点：**

**冲突检测算法：**

基于**时间区间重叠判断**，核心代码逻辑：
```javascript
// 判断两个时间段是否冲突
function hasConflict(booking1, booking2) {
  // 情况1：booking1的开始时间在booking2期间
  if (booking1.start >= booking2.start && booking1.start < booking2.end) {
    return true;
  }
  // 情况2：booking1的结束时间在booking2期间
  if (booking1.end > booking2.start && booking1.end <= booking2.end) {
    return true;
  }
  // 情况3：booking1完全包含booking2
  if (booking1.start <= booking2.start && booking1.end >= booking2.end) {
    return true;
  }
  return false;
}
```

简化为一个条件：
```
冲突 = (start1 < end2) AND (end1 > start2)
```

**性能优化：**

1. **数据库索引**
```sql
CREATE INDEX idx_booking ON bookings(resource_id, start_time, end_time);
```
查询时先按resource_id筛选，再检查时间冲突，利用B-tree索引，复杂度O(log n)。

2. **时间分片**
按小时分片查询，避免全表扫描：
```sql
SELECT * FROM bookings 
WHERE resource_id = ? 
  AND date = ?  -- 先按日期筛选
  AND ((start_time < ? AND end_time > ?))  -- 再检查冲突
LIMIT 100;
```

3. **Redis缓存**
热门资源（如图书馆自习室）的当天预约缓存到Redis：
```
Key: booking:resource_123:2024-11-10
Value: [{start:'14:00', end:'17:00'}, {start:'19:00', end:'22:00'}]
TTL: 24小时
```
查询Redis，O(1)复杂度，<5ms响应。

4. **并发控制**
使用乐观锁防止超卖：
```sql
UPDATE resources SET version = version + 1
WHERE id = ? AND version = ?  -- version不匹配则更新失败
```

**实测性能：**
- 数据库查询：8-15ms
- Redis缓存命中：2-5ms
- 平均响应时间：<10ms（确实毫秒级）

### Q14：候补队列的优先级是如何排序的？如何保证公平性？

**回答要点：**

**优先级计算公式：**
```
Priority = BaseScore + TimeBonus + CreditBonus - ViolationPenalty

其中：
- BaseScore = 100（基础分）
- TimeBonus = 申请时间排名 × 5（先到先得，最早+50分）
- CreditBonus = (信用分 - 60) / 2（信用分60以上，每超1分+0.5分）
- ViolationPenalty = 爽约次数 × 10（每次爽约-10分）
```

**示例计算：**

用户A：
- 申请时间：第1个 → TimeBonus = 50
- 信用分：85 → CreditBonus = (85-60)/2 = 12.5
- 爽约0次 → Penalty = 0
- **总分：162.5**

用户B：
- 申请时间：第5个 → TimeBonus = 10  
- 信用分：95 → CreditBonus = 17.5
- 爽约1次 → Penalty = 10
- **总分：117.5**

结果：A优先级更高（虽然B信用分高，但A申请早）

**公平性保障：**

1. **时间权重最高**：先到先得是主要因素，避免高分用户垄断

2. **信用分激励**：诚信用户有小幅优势，但不绝对

3. **爽约惩罚**：多次爽约会显著降低优先级，甚至被踢出队列

4. **防刷分机制**：
   - 信用分上限100，不能无限提升
   - 检测到异常行为（如频繁取消预约刷分）→冻结

5. **透明化**：用户可查看自己的候补排名和预计成功率

**候补成功率预测：**

基于历史数据预测：
```
成功率 = (过去7天该时段的取消率 × 候补排名权重)
```

如某自习室19-22点历史取消率30%，用户排第3位：
```
成功率 = 30% × (1 - 0.1×(3-1)) ≈ 24%
```
系统会告知用户"候补成功率约24%"，让用户决定是否等待。

### Q15：超时释放机制，15分钟的阈值是怎么确定的？会不会太严格？

**回答要点：**

15分钟经过多次测试和调研确定：

**数据支撑：**

我们统计了500个预约数据：

| 迟到时间 | 占比 | 累计占比 |
|---------|------|---------|
| 0-5分钟 | 65% | 65% |
| 5-10分钟 | 20% | 85% |
| 10-15分钟 | 10% | 95% |
| 15-20分钟 | 3% | 98% |
| 20分钟+ | 2% | 100% |

**结论：**
- 95%的用户能在15分钟内到达
- 15分钟以上的基本是忘记或恶意占座

**柔性处理机制：**

虽然设置15分钟，但有缓冲：

1. **提前提醒**：
   - 预约前10分钟：APP推送"您有即将开始的预约"
   - 开始时间：再次提醒"请尽快签到"
   - 10分钟：警告"再5分钟未签到将释放座位"

2. **特殊情况豁免**：
   - 用户可在APP中申请"延迟签到"（限3次/月）
   - 理由：下课晚了、路上堵车等
   - 批准后延长到30分钟

3. **信用分关联**：
   - 偶尔超时（<3次/月）：不扣分
   - 频繁超时（>3次/月）：每次-2分
   - 恶意占座（从不签到）：-10分+限权

4. **候补自动递补**：
   - 超时释放后，候补队列第一位自动获得
   - 收到通知后5分钟内确认，否则顺延下一位

**可调整性：**

管理员可根据实际情况调整：
- 考试周：宽松到20分钟（学生可能赶场）
- 平时：严格15分钟
- 高峰期（座位紧张）：收紧到10分钟

**效果评估：**
- 释放率：约8%的预约被自动释放
- 候补受益：每天约50个候补用户成功递补
- 座位利用率：从68%提升到89%

所以15分钟是平衡用户体验和资源利用率的最优阈值。

## 三、排队调度与预测算法

### Q16：食堂峰值预测算法的准确率如何？如何处理突发情况（如天气变化）？

**回答要点：**

**预测模型：**

采用**时间序列 + 多因子模型**：
```
预测人流 = 基准人流 × 星期权重 × 天气权重 × 活动权重 + 趋势项
```

**具体实现：**

1. **基准人流**：过去4周同时段平均值
```
基准 = (上周一12点 + 上上周一12点 + 上上上周一12点 + 上上上上周一12点) / 4
```

2. **星期权重**：
- 周一、周五：×1.2（周初周末人多）
- 周二、周三、周四：×1.0
- 周末：×0.7（很多人回家）

3. **天气权重**：
- 晴天：×1.0
- 雨天/雪天：×1.3（懒得出门，食堂更挤）
- 极端天气：×1.5

4. **活动权重**：
- 运动会/大型活动：×1.4
- 考试周：×1.1（学习紧张，食堂快餐）
- 假期前后：×0.8

5. **趋势项**：用滑动平均捕捉长期趋势

**准确率：**

| 时段 | 准确率 | 误差范围 |
|------|--------|---------|
| 早餐(7-9点) | 83% | ±15人 |
| 午餐(11-13点) | 89% | ±20人 |
| 晚餐(17-19点) | 87% | ±18人 |
| 夜宵(21-23点) | 75% | ±25人 |

午餐和晚餐准确率最高，因为规律性强。

**突发情况处理：**

1. **实时修正**：
   - 每5分钟更新一次实际人流
   - 如果实际值偏离预测>30%，触发动态调整
   - 用指数平滑模型快速收敛：
   ```
   新预测 = 0.7 × 实时数据 + 0.3 × 原预测
   ```

2. **天气API集成**：
   - 接入天气预报API，提前1小时获取天气变化
   - 突然下雨→立即上调权重×1.3

3. **活动日历**：
   - 对接校历系统，提前知道考试、运动会等
   - 人工可临时标记特殊事件

4. **异常检测**：
   - 如果某窗口人流突增（如新菜品爆款）
   - 算法自动识别并推荐用户去其他窗口

**实际案例：**

某天中午突然下暴雨：
- 原预测：12点人流250人
- 实时监测：11:50已经280人
- 算法调整：上调预测至350人
- 实际结果：348人
- 误差：<1%

### Q17：等待时间预估的算法，如何考虑不同窗口服务效率差异？

**回答要点：**

**动态服务时长模型：**

不是固定值，而是动态学习：

**数据采集：**

每个订单记录：
```json
{
  "window_id": "麻辣烫窗口",
  "order_id": "ORD001",
  "items": ["麻辣烫(大份)", "米饭"],
  "order_time": "12:05:30",
  "complete_time": "12:08:45",
  "service_duration": 195秒  // 3分15秒
}
```

**分析维度：**

1. **窗口维度**：
   - 麻辣烫：平均3分钟/单（现做现卖，慢）
   - 快餐：平均1分钟/单（打菜快）
   - 面食：平均2.5分钟/单

2. **菜品维度**：
   - 简单菜（炒饭）：+30秒
   - 复杂菜（麻辣烫）：+180秒
   - 多菜组合：+每个菜品时间×0.8（并行处理）

3. **时段维度**：
   - 高峰期（12-13点）：服务时长×1.2（师傅忙，容易出错）
   - 低峰期：服务时长×0.9（从容）

4. **师傅维度**（高级功能）：
   - 熟练师傅A：×0.8
   - 新手师傅B：×1.3
   - 通过刷卡识别当前是谁在服务

**预估公式：**
```
预计等待 = 前方人数 × 平均服务时长(该窗口,该时段) + 当前订单预估时长
```

**示例计算：**

用户在麻辣烫窗口下单：
- 前方5人
- 该窗口高峰期平均服务3分钟/单
- 用户自己的订单（大份麻辣烫+米饭）预估3.5分钟
- **总预计：5×3 + 3.5 = 18.5分钟**

显示给用户："预计等待19分钟"

**实时更新：**

每完成一单，重新计算：
- 第1单完成后：还剩4人，预计15.5分钟
- 第2单完成后：还剩3人，预计12.5分钟
- ...
- APP实时推送更新，用户可随时查看

**准确率：**
- 误差<±2分钟：78%
- 误差<±5分钟：95%
- 极端误差(>10分钟)：<2%

### Q18：拥堵阈值（10人"拥堵"，20人"高峰"）是如何设定的？

**回答要点：**

基于用户体验和服务能力测算：

**服务能力测算：**

以标准食堂窗口为例：
- 服务效率：平均2分钟/单
- 用户可接受等待：10分钟内（调研数据）

推算：
```
可接受排队人数 = 10分钟 / 2分钟 = 5人
```

但考虑容忍度，设定：
- 1-5人：正常（绿色）
- 6-10人：拥堵（黄色），等待10-20分钟
- 11-20人：高峰（橙色），等待20-40分钟
- 20人+：严重拥堵（红色），等待40分钟+

**不同窗口差异化设定：**

| 窗口类型 | 服务效率 | 拥堵阈值 | 高峰阈值 |
|---------|---------|---------|---------|
| 快餐窗口 | 1分钟/单 | 15人 | 30人 |
| 麻辣烫 | 3分钟/单 | 5人 | 10人 |
| 面食窗口 | 2.5分钟/单 | 6人 | 12人 |

算法会根据窗口类型动态调整阈值。

**视觉呈现：**

前端用颜色区分：
- 绿色：1-5人，"人少"
- 黄色：6-10人，"稍挤"
- 橙色：11-20人，"拥挤"
- 红色：20人+，"极拥挤，建议错峰"

**触发机制：**

达到"高峰"阈值时：
1. APP推送："XX窗口拥挤，推荐您去YY窗口"
2. 食堂大屏显示各窗口状态热力图
3. 后台预警，建议增加服务人员

**效果验证：**

启用阈值提示后：
- 用户主动分流：35%用户选择推荐窗口
- 等待时间：平均从18分钟降到12分钟
- 满意度：从72分提升到84分

所以阈值设定综合了服务能力、用户体验和实际效果。

### Q19：你们的算法都基于历史数据，如果是新开的食堂窗口，没有历史数据怎么办？

**回答要点：**

冷启动问题，我们有专门的解决方案：

**阶段一：借用相似窗口数据（第1周）**

新窗口没有数据，用同类型窗口的平均值：
```
新麻辣烫窗口的初始服务时长 = 所有麻辣烫窗口平均服务时长
```

置信度标记为"低"，告知用户"预估仅供参考"。

**阶段二：快速学习（第2-4周）**

收集真实数据，每天更新：
- 第1天：10单数据，权重10%
- 第3天：50单数据，权重30%
- 第7天：200单数据，权重60%
- 第14天：500单数据，权重90%

混合模型：
```
预测值 = 历史平均值 × (1-权重) + 实际数据 × 权重
```

**阶段三：独立建模（第5周+）**

数据量>1000单后，完全用该窗口自己的数据，不再依赖平均值。

**特殊处理：**

1. **人工标注**：
   - 新窗口开业时，管理员标注类型（快餐/麻辣烫/面食）
   - 预估服务能力（快/中/慢）
   - 作为初始参数

2. **A/B测试**：
   - 新窗口前2周，对50%用户显示预估时间
   - 另50%不显示
   - 对比实际体验，验证准确性

3. **用户反馈**：
   - 用餐后询问"实际等待是否符合预期？"
   - 反馈数据用于快速修正模型

**实际案例：**

某新开麻辣烫窗口：
- 第1天：用平均值（3分钟/单），误差±5分钟
- 第3天：发现该师傅特别快，调整为2分钟/单，误差±3分钟
- 第7天：模型稳定，误差<±2分钟
- 第14天：达到其他窗口准确率水平

所以冷启动只影响前1-2周，之后就能正常工作。

## Q1：AI偏好分析算法的六步流程，能详细讲解每一步的技术实现吗？

**回答要点（非常详细）：**

**第一步：识别对话类型与加载历史数据**

用户进入不同模块时，前端传递module_type参数。从MySQL检索最近50条历史对话：
```sql
SELECT content, timestamp FROM user_ai_conversations 
WHERE user_id = ? AND module_type = ? 
ORDER BY timestamp DESC LIMIT 50
```

**第二步：NLP关键词提取**

(1) jieba分词："我想要靠窗安静的位置" → ["靠窗","安静","位置"]

(2) 三维度词库匹配：
- 位置：["靠窗","角落","中间","靠门","靠前","靠后"]
- 环境：["安静","热闹","采光好","通风","空调"]  
- 设施：["电源","台灯","大桌子","软座椅"]

(3) 模糊匹配（创新点）：
- "低一些/矮一点" → "低楼层"
- "亮一点/光线好" → "采光好"

**第三步：TF-IDF权重计算与聚类**

(1) 统计词频：如"靠窗"出现40次/50次 = 80%

(2) 跨用户IDF（改进版）：
```
IDF = log(总用户数 / 包含该词的用户数)
Weight = TF × IDF
```

(3) 标记核心偏好：>50%高频，30-50%中频，<30%低频

(4) 多维聚类：按位置/环境/设施分组

**第四步：生成个性化洞察**

输入偏好数据，CoreAgent生成自然语言总结：
"根据您过去50次对话，您偏好靠窗或角落位置（高频80%、60%），倾向安静且采光好的环境（高频70%、55%）"

**第五步：可视化展示与注入前缀**

(1) 3秒动画展示分析过程
(2) 热力图展示偏好频率
(3) 构建System Prompt：
```
[用户偏好]
- 位置：靠窗(80%)，角落(60%)
- 环境：安静(70%)，采光好(55%)
请优先推荐符合偏好的资源
```

**第六步：AI模型处理与持续优化**

AI理解偏好后优先推荐，对话轮次从5.2降到3.6，提升30%。每次对话存储，形成学习闭环。

## Q2：TF-IDF的IDF在单用户场景下如何有意义？

**回答要点：**

我们用"跨用户IDF"改进算法。维护全局词频统计：
```
IDF = log(总用户数 / 包含该词的用户数)
```

示例：
- "座位"：4950/5000用户说过，IDF≈0.01（通用词，权重低）
- "靠窗"：2000/5000，IDF≈0.40（常见偏好）
- "角落"：800/5000，IDF≈0.80（个性化偏好，权重高）

最终权重 = 用户TF × 跨用户IDF

**意义：**
1. 区分通用需求vs个性化需求
2. 突出真实偏好特征
3. 处理冷启动（新用户用同类用户平均偏好）

## Q3：模糊匹配规则是手动维护还是算法学习的？

**回答要点：**

当前：手动维护 + 算法辅助混合模式

**阶段一：手动核心规则（200条）**

存储结构：
```
原始表达 | 标准关键词 | 置信度 | 场景
"低一些" | "低楼层" | 0.95 | 自习室/教室
"亮一点" | "采光好" | 0.92 | 自习室
```

匹配流程：精确匹配 → 编辑距离模糊匹配 → 置信度打折

**阶段二：算法辅助扩展（规划中）**

1. 收集未匹配表达
2. 语义聚类高频新词
3. 人工审核确认映射
4. A/B测试验证准确率>90%后上线

**为何不完全自动？**

1. 200条规则覆盖90%场景，够用
2. 手动规则准确性更高（如"高一点"在不同场景含义不同）
3. 性能更优（查询快，无需模型推理）

## Q4：偏好分析的实时性如何？会卡顿吗？

**回答要点：**

多层优化，完全无感：

**第一层：异步预计算**
- 每天凌晨2点批量计算所有用户偏好→存Redis
- 新对话后触发增量更新→加入队列→后台异步处理（延迟10秒）
- 用户发起对话→直接从Redis读取→<10ms

**第二层：增量计算**
- 只分析新对话（50ms）
- 更新词频（20ms）
- 重算权重（30ms）
- 总计100ms，后台完成

**第三层：降级策略**
- Redis失效→首次对话不用偏好→同时触发计算（3-5秒）→第二次开始生效

**实测数据：**
- Redis读取：8-12ms
- 首次计算：2-5秒
- 增量更新：100-200ms（异步）
- 用户感知：0ms（无感）

## Q6：历史数据取50条的依据是什么？为什么不是30或100条？

**回答要点：**

经过实验验证选择50条：

**实验对比：**

| 历史条数 | 计算耗时 | 准确率 | 覆盖时长 |
|---------|----------|--------|---------|
| 10条 | 0.5秒 | 68% | 约2周 |
| 30条 | 1.2秒 | 82% | 约1.5月 |
| **50条** | **2.3秒** | **89%** | **约3月** |
| 100条 | 5.1秒 | 90% | 约6月 |
| 200条 | 11.8秒 | 91% | 约1年 |

**选择50的理由：**

1. **准确率达标**：89%已经很高，再增加提升不明显（边际效应递减）

2. **性能平衡**：2.3秒可接受，100条的5秒太慢

3. **时效性**：3个月内的偏好最有参考价值。太久远的数据（如1年前）用户偏好可能已改变

4. **数据量充足**：日均活跃用户一般2-3周会有50条对话，覆盖面广

5. **存储成本**：50条×平均200字=1万字符，存储和计算都可控

**特殊处理：**

- 新用户<50条：用实际所有记录
- 超活跃用户>500条/月：只取最近50条，避免计算爆炸
- 冷启动用户=0条：用同专业平均偏好作为初始值

## Q7：偏好会随时间变化，你们如何处理偏好漂移？

**回答要点：**

非常好的问题！我们确实考虑了偏好的时效性：

**第一，时间衰减权重**

不是所有历史对话权重相同，我们引入时间衰减因子：
```
TimeWeight = e^(-λ × days_ago)
FinalWeight = TF × IDF × TimeWeight
```

λ=0.01表示每天衰减1%。举例：
- 今天的对话：TimeWeight = 1.0
- 30天前的对话：TimeWeight = e^(-0.01×30) ≈ 0.74
- 90天前的对话：TimeWeight = e^(-0.01×90) ≈ 0.41

越久远的偏好，权重越低，让算法更关注近期偏好。

**第二，偏好稳定度监控**

我们计算偏好稳定度指标：
```
稳定度 = (近30天偏好 ∩ 全部偏好) / (近30天偏好 ∪ 全部偏好)
```

如果稳定度<60%，说明偏好变化较大，会：
1. 提高近期权重（λ调整为0.02，衰减更快）
2. 触发偏好重置提示："检测到您的偏好可能有变化，是否重新分析？"

**第三，季节性偏好**

校园场景有明显季节特征：
- 夏天：用户更偏好"空调""通风""阴凉"
- 冬天：更偏好"暖气""向阳""保暖"

我们维护季节词库，根据当前季节动态调整权重。

**第四，自动重置机制**

满足以下条件自动触发偏好重新分析：
1. 距离上次计算>3个月
2. 新增对话>20条
3. 稳定度<60%
4. 用户主动点击"刷新偏好"

## Q8：如果用户有多种偏好（有时靠窗，有时角落），算法如何处理？

**回答要点：**

这是真实场景，我们支持多偏好并存：

**第一，多偏好识别**

不是只保留最高频的，而是保留所有高频+中频偏好：
```
位置偏好：
- 靠窗：80%（高频）
- 角落：60%（中频）
- 中间：25%（低频，不保留）
```

推荐时会说："您偏好靠窗(80%)或角落(60%)位置"，给出两类选择。

**第二，场景化偏好**

我们发现用户偏好与时间/目的有关，所以引入上下文：

时段偏好：
```
早上(8-12点)：用户70%选"采光好"（学习效率高）
下午(14-18点)：用户65%选"安静"（避免困倦需专注）
晚上(19-22点)：用户55%选"角落"（人少更安静）
```

目的偏好（通过对话识别）：
```
学习场景："靠窗"+"安静"+"电源"
社交场景："中间"+"热闹"+"大桌子"
```

推荐时结合当前时段和目的，优先级排序。

**第三，动态调整**

每次预约后收集反馈：
- 用户选了推荐：该偏好权重+5%
- 用户未选推荐：该偏好权重-3%
- 用户主动改选：新选择权重+10%

形成持续优化闭环。

如果偏好矛盾（如"靠窗"+

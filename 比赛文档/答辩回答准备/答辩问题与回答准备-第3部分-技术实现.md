## 一、技术架构与选型

### Q20：为什么选择CodeWave低代码平台，而不是传统的前后端分离开发？

**回答要点：**

基于开发效率、学习成本和生态整合三方面考虑：

**1. 开发效率显著提升**

传统开发 vs CodeWave对比：

| 功能模块 | 传统开发 | CodeWave | 效率提升 |
|---------|---------|----------|---------|
| 数据库设计 | 手写SQL建表 | 可视化建模 | 60% |
| CRUD接口 | 手写代码 | 自动生成 | 80% |
| 权限控制 | 自己实现 | 内置模块 | 90% |
| 表单校验 | 手写逻辑 | 配置规则 | 70% |
| 部署上线 | 手动部署 | 一键发布 | 85% |

整体开发时间从预估3个月缩短到1个月。

**2. 学习成本低**

我们团队5人，技术水平参差不齐：
- 2人有全栈经验
- 2人只会前端
- 1人主攻算法

传统开发需要学习：Spring Boot、MyBatis、Redis、Nginx、Docker等，学习周期长。

CodeWave只需要：
- 理解可视化编排逻辑
- 学习少量自定义代码
- 1周即可上手

**3. 生态整合优势**

CodeWave + CoreAgent + 云信IM 是网易全家桶：
- **统一账号体系**：CodeWave用户直接映射到IM accid
- **统一权限模型**：角色权限自动同步
- **统一部署运维**：共用监控告警体系
- **技术支持**：网易官方文档完善，社区活跃

如果用传统开发，这些集成需要大量对接工作。

**4. 并非完全低代码**

我们也写了大量自定义代码：
- AI偏好分析算法：纯代码实现
- 预约冲突检测：自定义SQL优化
- 排队预测模型：Python脚本
- IM锚点解析：自定义前端逻辑

CodeWave支持代码扩展，可以在需要的地方写代码，兼顾效率和灵活性。

**总结：**
CodeWave适合我们这种"复杂业务 + 创新算法 + 时间紧张"的场景。标准CRUD用低代码，核心算法用代码，是最优组合。

### Q21：CoreAgent智能体具体如何工作？和普通的API调用GPT有什么区别？

**回答要点：**

CoreAgent不是简单的GPT API封装，它是一个智能体编排平台：

**核心区别：**

| 维度 | 普通GPT API | CoreAgent智能体 |
|------|------------|----------------|
| 能力范围 | 只能对话 | 对话+工具调用+工作流 |
| 知识来源 | 仅预训练知识 | 可接入自定义知识库 |
| 多轮记忆 | 需手动管理上下文 | 自动管理会话记忆 |
| 工具调用 | 需手动解析函数 | 内置工具编排引擎 |
| 可观测性 | 黑盒 | 可视化调试追踪 |

**具体工作流程：**

以自习室智能预约为例：

(1) **用户输入**："帮我找个明天下午的自习室座位"

(2) **意图识别**：CoreAgent分析意图→"预约自习室"

(3) **参数提取**：
- 时间：明天下午（转换为具体时间戳）
- 需求：未明确说明

(4) **调用偏好分析工具**（我们自定义的函数）：
```json
{
  "tool_name": "get_user_preference",
  "params": {"user_id": 12345, "scene": "study_room"}
}
```
返回：{"position": "靠窗", "environment": "安静", "facility": "电源"}

(5) **调用座位查询工具**：
```json
{
  "tool_name": "search_available_seats",
  "params": {
    "date": "2024-11-11",
    "time_range": "14:00-17:00",
    "preferences": {"position": "靠窗", "environment": "安静"}
  }
}
```
返回：3个符合条件的座位

(6) **生成回复**：
"根据您的偏好（靠窗、安静、有电源），为您找到3个座位..."

(7) **等待用户选择**：用户选座位后，调用预约工具完成预约

**关键优势：**

1. **工作流编排**：多个步骤自动串联，开发者只需定义工具，编排逻辑由CoreAgent完成

2. **知识库集成**：我们上传了校园常见问题、座位分布图、使用指南等文档，AI可以直接检索回答

3. **多模型切换**：可以配置不同场景用不同模型（如简单问答用小模型省成本，复杂推理用大模型）

4. **可视化调试**：每次调用都能看到完整链路，方便排查问题

5. **版本管理**：智能体配置支持版本回滚，A/B测试

**技术实现：**

我们在CodeWave后端注册了自定义函数：
```javascript
// 注册偏好分析工具
CoreAgent.registerTool({
  name: "get_user_preference",
  description: "获取用户的历史偏好",
  parameters: {
    user_id: "number",
    scene: "string"
  },
  handler: async (params) => {
    // 调用我们的偏好分析算法
    return await UserPreferenceService.analyze(params);
  }
});
```

CoreAgent会在需要时自动调用这些工具，无需手动判断和解析。

### Q22：你们的系统用MySQL存储，为什么不用MongoDB等NoSQL数据库？

**回答要点：**

基于数据特征和业务需求选择关系型数据库：

**为什么选MySQL：**

**1. 数据结构化程度高**

我们的核心数据都是结构化的：
- 用户信息：固定字段（学号、姓名、学院）
- 订单数据：订单号、商品、价格、状态
- 预约记录：资源ID、时间段、用户ID
- 课程表：课程、教室、时间、教师

这些数据字段明确，关系清晰，非常适合关系型数据库。

**2. 事务需求强**

很多场景需要ACID事务保证：

**预约场景**：
```sql
BEGIN TRANSACTION;
-- 检查座位是否可用
SELECT status FROM seats WHERE id = ? FOR UPDATE;
-- 创建预约记录
INSERT INTO bookings (...);
-- 更新座位状态
UPDATE seats SET status = 'occupied' WHERE id = ?;
COMMIT;
```

如果中途失败（如断电），要么全部成功，要么全部回滚，不能出现"座位被占用但没有预约记录"的不一致状态。

MongoDB虽然也支持事务，但性能和成熟度不如MySQL。

**3. 复杂查询需求**

我们有大量JOIN查询和聚合统计：

**数据看板查询**：
```sql
SELECT 
  o.date, 
  COUNT(o.id) as order_count,
  SUM(o.amount) as revenue,
  u.name as merchant_name
FROM orders o
JOIN merchants m ON o.merchant_id = m.id
JOIN users u ON m.user_id = u.id
WHERE o.date >= ?
GROUP BY o.date, u.name
ORDER BY revenue DESC;
```

这种多表关联在关系型数据库中非常高效，在NoSQL中需要多次查询或数据冗余。

**4. 成熟的生态**

- ORM工具成熟（如TypeORM、Sequelize）
- 备份恢复工具完善
- 运维经验丰富
- 性能优化方案多

**什么场景我们用了NoSQL：**

虽然主库是MySQL，但我们也用了Redis（NoSQL）：

1. **缓存层**：热点数据（如热门座位状态）
2. **会话存储**：用户登录态
3. **计数器**：实时统计（如在线人数）
4. **消息队列**：异步任务（如发送通知）

所以我们是**MySQL（主存储） + Redis（缓存/队列）**的混合架构。

**如果有非结构化数据：**

对于对话记录、AI生成的文本等非结构化数据，我们用对象存储（OSS），不放数据库。

**总结：**
技术选型没有绝对好坏，要看具体场景。我们的数据特征和业务需求更适合MySQL。

### Q23：系统的并发能力如何？能支撑多少用户同时在线？

**回答要点：**

**性能测试数据：**

我们做了压力测试，使用JMeter模拟并发：

| 场景 | 并发用户数 | TPS | 平均响应时间 | 成功率 |
|------|-----------|-----|------------|--------|
| 用户登录 | 500 | 450 | 120ms | 99.8% |
| 浏览订单列表 | 1000 | 850 | 180ms | 99.5% |
| 创建订单 | 500 | 420 | 250ms | 99.2% |
| 预约座位 | 300 | 280 | 300ms | 98.9% |
| IM发送消息 | 1000 | 900 | 100ms | 99.9% |

**瓶颈分析：**

1. **数据库连接池**：
   - 当前配置：最大100个连接
   - 超过300并发时开始排队
   - 优化：引入读写分离，主库写，从库读

2. **CPU密集操作**：
   - AI偏好分析：需要2-3秒计算
   - 优化：异步处理+缓存结果

3. **网络带宽**：
   - 图片上传是瓶颈
   - 优化：接入CDN加速

**实际承载能力估算：**

一个中型大学：
- 在校生：20,000人
- 日活用户：30%（6,000人）
- 高峰时段在线：20%（1,200人）
- 同时操作：10%（120人）

我们的系统可以支撑**300-500并发**，对于中型大学完全足够。

**扩展性设计：**

如果用户规模扩大，可以横向扩展：

1. **应用层无状态**：多台服务器负载均衡
2. **数据库分库分表**：按学院或功能模块拆分
3. **缓存集群**：Redis主从+哨兵
4. **容器化部署**：Docker + Kubernetes弹性伸缩

理论上可以支撑**10万+日活**。

**降级策略：**

极端高峰（如选课、抢座）时：
1. 限流：每秒最多处理500请求
2. 降级：关闭非核心功能（如AI推荐）
3. 排队：超出的用户进入虚拟队列
4. 扩容：自动增加服务器实例

## 二、数据安全与隐私

### Q24：学生的个人信息和隐私数据如何保护？

**回答要点：**

**多层防护体系：**

**第一层：数据加密**

1. **传输加密**：全站HTTPS（TLS 1.3）
2. **存储加密**：
   - 敏感字段（手机号、身份证）AES-256加密
   - 数据库全盘加密（透明数据加密TDE）
3. **密码存储**：bcrypt哈希+盐（不可逆）

**第二层：访问控制**

1. **角色权限（RBAC）**：
```
学生角色：只能看自己的数据
食堂管理员：只能看自己食堂的订单
校级管理员：可以看汇总数据，不能看个人详情（除非审批）
```

2. **数据脱敏**：
   - 管理员查看订单：学号显示为"202101****"
   - 导出报表：手机号显示为"138****5678"

3. **操作审计**：
   - 所有敏感数据访问记录到日志
   - 包括：谁、什么时间、访问了什么数据、是否成功
   - 日志不可篡改，定期审计

**第三层：最小化原则**

1. **只收集必要信息**：
   - 必须：学号、姓名、学院（实名认证）
   - 可选：头像、签名、兴趣（用户自愿）
   - 不收集：身份证号、家庭住址（非必需）

2. **数据过期删除**：
   - 订单数据保留1年
   - 聊天记录默认7天
   - 毕业生数据匿名化或删除

**第四层：合规认证**

1. **符合《个人信息保护法》**：
   - 明确告知隐私政策
   - 用户授权同意后才收集
   - 支持用户查询、更正、删除自己的数据

2. **符合《网络安全法》**：
   - 定期安全评估
   - 应急响应预案
   - 数据备份机制

3. **校方监管**：
   - 数据治理委员会审批敏感数据访问
   - 定期安全审计
   - 第三方渗透测试

**第五层：技术防护**

1. **SQL注入防护**：参数化查询，ORM框架
2. **XSS防护**：输入过滤，输出编码
3. **CSRF防护**：Token验证
4. **DDoS防护**：CDN + 限流
5. **漏洞扫描**：每周自动扫描，及时修复

**用户可控**：

学生可以自主：
- 查看自己的所有数据
- 导出数据副本
- 删除部分数据（如聊天记录）
- 注销账号（匿名化处理）

### Q25：如果发生数据泄露，你们有应急预案吗？

**回答要点：**

有完整的安全事件应急响应机制：

**响应流程（分钟级）：**

**阶段一：检测与确认（0-15分钟）**

1. **自动检测**：
   - 异常登录：IP归属地突变、大量失败尝试
   - 异常查询：单用户短时间大量数据读取
   - 异常导出：批量导出敏感数据

2. **告警触发**：
   - 短信通知技术负责人
   - 邮件通知安全团队
   - 钉钉群紧急@所有人

3. **初步确认**：
   - 查看监控日志
   - 确认是否真的泄露，还是误报

**阶段二：止损（15-30分钟）**

1. **立即隔离**：
   - 封禁异常账号
   - 切断疑似攻击来源IP
   - 如果是内部人员，立即撤销权限

2. **锁定数据**：
   - 临时关闭敏感数据访问
   - 数据库只读模式
   - 备份当前状态用于取证

3. **通知用户**（如果确认泄露）：
   - APP/短信通知受影响用户
   - 建议立即修改密码
   - 提供客服热线

**阶段三：修复（30分钟-24小时）**

1. **漏洞修复**：
   - 定位漏洞点
   - 紧急修补
   - 全面测试

2. **数据恢复**：
   - 如果数据被篡改，从备份恢复
   - 验证数据完整性

3. **加固防护**：
   - 升级安全策略
   - 增加监控规则
   - 加强访问控制

**阶段四：复盘与改进（24小时-1周）**

1. **事件分析**：
   - 根因分析（5 Whys）
   - 时间线梳理
   - 影响范围评估

2. **责任追究**：
   - 技术问题：技术负责
   - 人为问题：纪律处分
   - 外部攻击：报案处理

3. **流程改进**：
   - 更新应急预案
   - 组织安全培训
   - 优化监控告警

**演练机制**：

每季度进行一次模拟演练：
- 模拟SQL注入攻击
- 模拟内部人员越权访问
- 测试响应时间和处理流程

最近一次演练：检测到响应时间12分钟，达标。

**法律合规**：

按照《网络安全法》要求：
- 72小时内向监管部门报告
- 及时通知受影响用户
- 配合调查取证

**保险保障**：

购买了网络安全保险，覆盖：
- 数据泄露造成的损失
- 法律诉讼费用
- 声誉修复成本

| 生产环境 | 正式运行 | 真实数据 | 生产服务器集群 |

```yaml
# GitLab CI配置示例
stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - npm install

test:
  stage: test

    - npm run test

  stage: deploy

    - main
```

3. **自动测试**：
   - 单元测试：覆盖率>80%
   - 集成测试：核心流程走通
   - 失败自动回滚

4. **人工审批**：
   - 测试环境自动部署

   - 监控异常（错误率>5%）
   - 自动回滚到上一版本

**容器化部署：**

使用Docker + Docker Compose：


**监控告警：**

   - CPU、内存、磁盘、网络

   - 错误率>5%：P0级别，立即短信
   - 响应时间>2秒：P1级别，钉钉通知

   - 全量备份：每天凌晨3点

   - Git仓库多地备份
   - 容器镜像保留最近10个版本

3. **配置备份**：

定期进行灾难恢复演练，确保能在4小时内恢复服务。

### Q27：CodeWave平台如果出现故障或停服，你们的系统会受影响吗？

**回答要点：**

这是一个关于平台依赖风险的好问题：

**依赖分析：**

我们对CodeWave的依赖分为两类：

**1. 开发时依赖（不影响运行）**

- 可视化建模工具
- 代码生成器
- 部署发布工具

这些只在开发阶段使用，生产环境不依赖。即使CodeWave停服，已部署的系统不受影响。

**2. 运行时依赖（部分影响）**

- 登录认证服务
- 权限管理模块
- 配置中心

这些是运行时调用的，如果CodeWave停服会有影响。

**风险缓解措施：**

**措施一：本地缓存**

登录认证Token有效期24小时，用户在Token有效期内不受影响：
```javascript
// Token验证逻辑
if (tokenValid && !expired) {
  // 直接放行，不调用CodeWave
  return next();
} else {
  // 才调用CodeWave验证
  return validateWithCodeWave();
}
```

**措施二：降级方案**

如果检测到CodeWave不可用：
1. 启用本地权限验证（基于上次同步的权限数据）
2. 关闭需要实时验证的功能
3. 显示告警信息："部分功能暂时不可用"

**措施三：数据导出**

关键数据定期导出备份：
- 用户信息
- 角色权限配置
- 系统配置

CodeWave停服时可以用备份数据临时运行。

**措施四：迁移能力**

CodeWave生成的代码可以导出，理论上可以迁移到其他平台或纯代码项目。

**实际影响评估：**

- **短期停服（<1小时）**：几乎无影响（靠缓存和降级）
- **中期停服（1-24小时）**：部分功能受限（新用户无法注册，权限修改不生效）
- **长期停服（>24小时）**：需要启动迁移方案（2-3天可完成）

**服务等级协议（SLA）**：

网易CodeWave承诺：
- 可用性：99.9%（每年停服<9小时）
- 故障响应：<30分钟
- 数据不丢失保证

所以实际风险很低。

**总结：**
我们对CodeWave有一定依赖，但做了充分的风险准备，短期停服几乎无影响，长期停服有迁移方案。这是使用任何云平台都面临的共性问题，关键是做好风险管理。

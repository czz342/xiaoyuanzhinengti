## 一、冲突检测算法

### Q1：预约冲突检测为什么不用数据库悲观锁？

**四种方案对比：**

| 方案 | 冲突准确率 | 并发TPS | 响应时间 | 我们选择 |
|------|-----------|---------|---------|---------|
| 应用层检测 | 82% | 80 | 200ms | ❌有漏检 |
| 数据库悲观锁 | 100% | 12 | 3.5秒 | ❌太慢 |
| 唯一索引 | 0% | - | - | ❌不适用 |
| 乐观锁+Redis | 99.5% | 75 | 280ms | ✅最优 |

**为什么不用悲观锁：**

**问题1：性能瓶颈**
```sql
BEGIN TRANSACTION;
SELECT * FROM bookings WHERE seat_id = 101 FOR UPDATE;
-- 其他用户必须等待这个事务完成
-- 100个用户同时预约101座位，串行化处理
INSERT INTO bookings ...;
COMMIT;
```

实测：
- 10并发：TPS=8
- 100并发：TPS=12（锁竞争激烈）

**问题2：用户体验差**
- 等待时间：平均3.5秒
- 抢座高峰：等待5-8秒
- 用户会以为系统卡死

**问题3：锁粒度大**
- 锁住整行，影响该座位所有时间段的查询
- 其他时间段的预约也被阻塞

### Q2：乐观锁+Redis方案具体怎么实现的？

**四步流程：**

**步骤1：Redis分布式锁（快速失败）**
```javascript
// 尝试获取座位锁（10秒自动过期）
const lockKey = `lock:seat:${seatId}`;
const locked = await redis.set(lockKey, userId, {
  NX: true,  // 只有不存在才设置
  EX: 10     // 10秒过期
});

if (!locked) {
  // 立即失败，不阻塞
  return { success: false, message: '座位正在被预订，请稍后' };
}
```

**步骤2：数据库乐观检测**
```sql
-- 查询时间冲突（不加锁，快！）
SELECT COUNT(*) as conflict_count
FROM bookings
WHERE seat_id = ?
  AND status = 'confirmed'
  AND NOT (end_time <= ? OR start_time >= ?);
-- 逻辑：结束时间≤新开始 OR 开始时间≥新结束 = 不冲突
-- 取反 = 冲突

-- 如果conflict_count > 0，说明有冲突
```

**步骤3：版本号控制**
```sql
-- 座位表有version字段
UPDATE seats
SET status = 'occupied', 
    version = version + 1,
    updated_at = NOW()
WHERE id = ?
  AND version = ?  -- 乐观锁关键
  AND status = 'available';

-- affected_rows = 0 说明被别人抢了
```

**步骤4：释放锁**
```javascript
await redis.del(lockKey);
```

**关键优势：**

1. **快速失败**：Redis锁冲突<10ms返回
2. **并行处理**：不同座位可并行
3. **锁粒度小**：只锁单个座位
4. **性能高**：TPS=75，响应280ms

### Q3：0.5%的冲突漏检怎么处理？

**第1层：定时任务修复（每小时）**

```sql
SELECT b1.id as booking1, b2.id as booking2,
       b1.user_id, b2.user_id
FROM bookings b1, bookings b2
WHERE b1.seat_id = b2.seat_id
  AND b1.id < b2.id
  AND b1.status = 'confirmed'
  AND b2.status = 'confirmed'
  AND NOT (b1.end_time <= b2.start_time OR b1.start_time >= b2.end_time);

-- 发现冲突后：
-- 1. 标记为异常
-- 2. 通知双方用户
```

## 二、候补机制

### Q4：候补队列的优先级怎么算的？

**多因子优先级模型：**

```python
优先级分数 = 等待时长权重 × 40% 
          + 用户信用分权重 × 30%
          + 预约频次权重 × 20%
          + 特殊身份权重 × 10%
```

**具体计算：**

**因子1：等待时长（40%）**
```python
等待分钟 = (当前时间 - 加入候补时间).total_seconds() / 60
等待权重 = min(等待分钟 / 60, 1.0)  # 最高1.0
# 等待60分钟 = 满分
```

**因子2：用户信用分（30%）**
```python
# 信用分系统
信用分 = 基础分100 
        + 守约次数 × 2 
        - 爽约次数 × 5
        - 投诉次数 × 10

信用权重 = (信用分 - 60) / 40  # 归一化到0-1
# 信用分60以下 = 0分
# 信用分100 = 满分
```

**因子3：预约频次（20%）**
```python
# 最近30天预约成功次数
频次 = 最近30天预约成功次数
频次权重 = min(频次 / 10, 1.0)
# 预约10次以上 = 满分
```

**因子4：特殊身份（10%）**
```python
if 身份 == '考研学生' and 距离考研时间 < 60天:
    特殊权重 = 1.0
elif 身份 == '残疾学生':
    特殊权重 = 1.0
elif 身份 == '贫困生':
    特殊权重 = 0.5
else:
    特殊权重 = 0
```

**示例计算：**

```
用户A：
- 等待45分钟：45/60 = 0.75
- 信用分85：(85-60)/40 = 0.625
- 预约5次：5/10 = 0.5
- 普通学生：0

优先级 = 0.75×0.4 + 0.625×0.3 + 0.5×0.2 + 0×0.1
       = 0.3 + 0.1875 + 0.1 + 0
       = 0.5875

用户B：
- 等待20分钟：20/60 = 0.33
- 信用分95：(95-60)/40 = 0.875
- 预约12次：12/10 = 1.0
- 考研学生：1.0

优先级 = 0.33×0.4 + 0.875×0.3 + 1.0×0.2 + 1.0×0.1
       = 0.132 + 0.2625 + 0.2 + 0.1
       = 0.6945

用户B优先级更高（虽然等待时间短，但信用分高+考研身份）
```

### Q5：候补成功率怎么预测的？

**基于历史数据的概率模型：**

**数据收集：**
```sql
-- 统计最近30天的候补数据
SELECT 
  seat_type,
  time_slot,
  queue_position,
  COUNT(*) as total,
  SUM(CASE WHEN success = 1 THEN 1 ELSE 0 END) as success_count
FROM waitlist_history
WHERE created_at >= DATE_SUB(NOW(), INTERVAL 30 DAY)
GROUP BY seat_type, time_slot, queue_position;
```

**概率计算：**
```python
def predict_success_rate(seat_type, time_slot, queue_position):
    """
    预测候补成功概率
    """
    # 查询历史数据
    history = db.query("""
        SELECT success_count, total 
        FROM waitlist_stats
        WHERE seat_type = ?
          AND time_slot = ?
          AND queue_position = ?
    """, [seat_type, time_slot, queue_position])
    
    if history:
        base_rate = history['success_count'] / history['total']
    else:
        # 没有历史数据，使用全局平均
        base_rate = 0.3
    
    # 考虑实时因素
    current_queue_size = get_current_queue_size(seat_type, time_slot)
    
    if current_queue_size > 20:
        # 队列太长，降低概率
        base_rate *= 0.7
    elif current_queue_size < 5:
        # 队列很短，提高概率
        base_rate *= 1.2
    
    return min(base_rate, 1.0)
```

```
- 基础成功率：65%
- 当前队列：8人（正常）
- 预测成功率：65%

显示给用户："预计成功率65%，平均等待15分钟"
```

## 三、超时释放机制

### Q6：为什么选15分钟超时？5分钟或30分钟不行吗？

**测试不同超时时长：**

| 超时时长 | 座位利用率 | 用户满意度 | 投诉率 |
|---------|-----------|-----------|--------|
| 5分钟 | 92% | 72分 | 8%（太严格）|
| 10分钟 | 90% | 78分 | 4% |
| **15分钟** | **89%** | **84分** | **1.5%** ✅|
| 20分钟 | 86% | 85分 | 1% |
| 30分钟 | 78% | 86分 | 0.5%（太宽松）|

**选择15分钟的理由：**

**1. 用户到达时间分析**
```
统计1000次预约的实际签到时间：

准时到达（0-5分钟）：60%
延迟到达（5-10分钟）：25%
较晚到达（10-15分钟）：10%
很晚到达（15-20分钟）：3%
不来（>20分钟）：2%

累计分布：
5分钟内：60%
10分钟内：85%
15分钟内：95% ← 覆盖绝大多数
20分钟内：98%
```

15分钟能覆盖95%的正常到达用户。

**2. 场景容错考虑**

合理延迟场景：
- 教室走到自习室：5-8分钟
- 食堂吃完走过来：8-12分钟
- 临时接个电话：3-5分钟
- 找座位+放书包：2-3分钟

总计：最多15分钟合理。

**3. 避免恶意占座**

如果30分钟超时：
- 用户可以预约后慢悠悠来
- 座位浪费严重
- 候补用户等待太久

如果5分钟超时：
- 用户压力大（必须狂奔）
- 正常延迟也被释放（投诉高）

**4. 与候补机制平衡**

候补用户平均等待：
- 如果超时5分钟：等待可能很久（因为大部分人能在5-15分钟到）
- 如果超时15分钟：候补等待合理（15分钟内就能知道结果）
- 如果超时30分钟：候补等待太久（体验差）

## 四、智能推荐算法

### Q8：候选座位推荐的排序算法是什么？

**多维度评分模型：**

```python
总分 = 偏好匹配度 × 50%
     + 距离得分 × 25%
     + 环境质量 × 15%
     + 历史评价 × 10%
```

**维度1：偏好匹配度（50%）**
```python
# 用户偏好向量（来自AI偏好分析）
user_pref = {
  "position": {"靠窗": 0.8, "角落": 0.6},
  "environment": {"安静": 0.7, "采光好": 0.5},
  "facility": {"电源": 0.6}
}

# 座位特征向量
seat_feature = {
  "position": "靠窗",
  "environment": ["安静", "采光好"],
  "facility": ["电源", "台灯"]
}

# 匹配度计算（余弦相似度）
def calculate_preference_match(user_pref, seat_feature):
    score = 0
    
    # 位置匹配
    if seat_feature["position"] in user_pref["position"]:
        score += user_pref["position"][seat_feature["position"]] * 0.4
    
    # 环境匹配
    for env in seat_feature["environment"]:
        if env in user_pref["environment"]:
            score += user_pref["environment"][env] * 0.3
    
    # 设施匹配
    for fac in seat_feature["facility"]:
        if fac in user_pref["facility"]:
            score += user_pref["facility"][fac] * 0.3
    
    return min(score, 1.0)

# 示例：
# 座位101（靠窗、安静、有电源）
# 匹配度 = 0.8×0.4 + 0.7×0.3 + 0.6×0.3 = 0.32 + 0.21 + 0.18 = 0.71
```

**维度2：距离得分（25%）**
```python
def calculate_distance_score(user_location, seat_location):

    distance = haversine_distance(user_location, seat_location)
    
    # 转换为得分（距离越近分数越高）

        return 1.0
    elif distance < 100:
        return 0.9
    elif distance < 200:
        return 0.7
    elif distance < 500:
        return 0.4
    else:
        return 0.1
```

**维度3：环境质量（15%）**
```python
def calculate_environment_score(seat_id):
    # 综合评分
    score = 0
    
    # 噪音水平（传感器数据）
    noise_level = get_noise_level(seat_id)  # 分贝
    if noise_level < 40:
        score += 0.4  # 很安静
    elif noise_level < 50:
        score += 0.3
    else:
        score += 0.1
    
    # 光照强度（传感器数据）
    light_level = get_light_level(seat_id)  # 勒克斯
    if 300 < light_level < 500:
        score += 0.3  # 适中
    elif light_level > 500:
        score += 0.2  # 较亮
    else:
        score += 0.1  # 较暗
    
    # 温度舒适度
    temperature = get_temperature(seat_id)  # 摄氏度
    if 20 < temperature < 26:
        score += 0.3  # 舒适
    else:
        score += 0.1
    
    return score
```

**维度4：历史评价（10%）**
```python
def calculate_rating_score(seat_id):
    # 最近100次使用的平均评分
    avg_rating = db.query("""
        SELECT AVG(rating) 
        FROM seat_reviews
        WHERE seat_id = ?
        ORDER BY created_at DESC
        LIMIT 100
    """, [seat_id])
    
    # 5分制转为0-1
    return avg_rating / 5.0
```

**最终排序：**
```python
def rank_seats(user_id, available_seats):
    ranked_seats = []
    
    for seat in available_seats:
        # 计算各维度得分
        pref_score = calculate_preference_match(user_pref, seat)
        dist_score = calculate_distance_score(user_location, seat.location)
        env_score = calculate_environment_score(seat.id)
        rating_score = calculate_rating_score(seat.id)
        
        # 综合得分
        total_score = (pref_score * 0.5 +
                      dist_score * 0.25 +
                      env_score * 0.15 +
                      rating_score * 0.1)
        
        ranked_seats.append({
            'seat': seat,
            'score': total_score,
            'breakdown': {
                '偏好匹配': pref_score,
                '距离': dist_score,
                '环境': env_score,
                '评价': rating_score
            }
        })
    
    # 按得分降序排序
    ranked_seats.sort(key=lambda x: x['score'], reverse=True)
    
    return ranked_seats[:5]  # 返回前5个
```

## 五、性能优化

### Q9：预约创建的完整耗时是多少？

**分步耗时分析（100并发压测）：**

```
步骤1：Redis分布式锁
  - 尝试获取锁：3-8ms
  - 失败立即返回：<10ms

步骤2：数据库冲突检测
  - SELECT查询（有索引）：15-25ms
  - 无冲突：继续
  - 有冲突：立即返回（总计20-30ms）

步骤3：创建预约记录
  - INSERT操作：10-20ms
  - 更新座位状态：5-10ms

步骤4：释放Redis锁
  - DEL操作：2-5ms

步骤5：发送确认通知
  - 异步推送：不阻塞（后台处理）

总计：35-70ms（中位数45ms，P95为80ms）
```

**性能瓶颈识别：**
1. 数据库查询：15-25ms（最耗时）
2. INSERT操作：10-20ms
3. Redis操作：5-13ms

**优化措施：**
1. 索引优化：seat_id + time_range复合索引
2. 连接池：最大300连接
3. Redis集群：主从+哨兵
4. 异步通知：不阻塞主流程
